# 专业化写作

## 从素材走到成稿

先从用户材料中提取每个项目的事实：服务的场景、约束、本人角色、技术动作、交付物、结果与来源。材料没有的维度可以省略，不用空话填满。短任务在工作笔记中记录即可，不必额外生成表格交给用户。

把混在一起的内容按真正的项目目标组织。例如同一段中既有超低比特算法探索，又有大规模训练与芯片协同设计，两者目标、责任和成果不同，可以拆成两个项目；同一项目的多个工程动作不必各起一个宏大的项目名。

用户已经指定的项目结构优先。整体整理并采用默认定稿版式时，按“项目名 → 背景/职责 → 分项工作与成果”的视觉层级组织信息；缺少某类事实时省略对应字段，不用空话填满。局部文案请求可直接给紧凑段落。科研经历可用“问题 → 方法 → 实验结果”，论文标题、作者标记和发表状态保持准确。

专业化通常来自以下具体提升：

- 将工具清单解释为工程关系：在哪个框架、哪个环节实现了什么能力。
- 将“探索算法”细化为原有材料支持的问题、机制与验证方式。
- 将“对接其他团队”写清输入约束、技术接口或设计决策。
- 将“效果好”替换为已有的可核验结果；没有数字时，写实际完成的管线、分析工具、训练阶段或论文产出。

不要把文章作者或团队成果直接等同于个人独立完成的工作；论文公开方法可解释项目技术内容，个人分工仍以用户资料为准。

分别保存各项目的事实边界。不能把相邻项目的位宽、业务场景、方法或指标自动沿用到另一条经历；项目之间的关系需要材料支持。

## Owner 写法

按已确认事实选择责任层级：

| 实际责任 | 可以采用的表达 |
| --- | --- |
| 对指定项目整体负责 | 作为【项目名】项目 Owner，负责【已确认的责任范围】。 |
| 多位共同负责人 | 作为项目 Owner 之一，负责【明确的子范围】，与【相关团队】协同推进【有依据的任务】。 |
| 独立负责某模块 | 负责【模块名】的设计、实现与验证。是否是模块 Owner 取决于用户确认，不自动升级。 |
| 参与研发 | 参与【项目/模块】，完成【本人实际贡献】。 |

“负责方案设计、核心研发、实验验证”只在这些职责都有依据时使用；不自动补上需求管理、排期、带团队、资源协调或上线验收。“Owner”出现在职责句即可，不需要每条分项重复。

## 将技术与业务联系起来

采用因果关系：**业务场景 → 资源或性能约束 → 技术路线 → 预期价值/已实现结果**。

示例素材：

> 虚构教学示例：基于某公开低比特方法探索原生量化训练，示例假定应用场景涉及多种智能设备。

可改为：

> 面向手机、汽车及智能家居生态的模型应用需求，基于公开低比特方法探索原生量化训练。

若材料进一步确认是端侧大模型部署、目标是降低存储与推理开销，可丰富为：

> 面向手机、汽车及智能家居场景的端侧大模型部署需求，基于公开低比特方法探索原生量化训练，以降低模型存储与推理开销，为多设备场景提供轻量化模型支撑。

具体企业名称与生态名称来自本轮材料时可以保留。这里描述服务目标，并没有声称已经量产部署或已经实现跨设备协同。只有材料确实涉及多个业务环节的反馈和衔接，才使用“生态闭环”；仅表明适用场景时，“面向……需求”“支撑……场景”更准确。

## 前后示例

以下均为虚构教学示例，只演示表达方法，不能作为任何用户的事实来源。改写中出现的技术机制必须已经在其素材或可靠参考中得到支持。

### 1. 从宽泛职责到明确工程贡献

原文：

> 负责低精度训练基础设施建设，包括训练方案探索和监控系统搭建。

在角色和具体工作已确认的前提下：

> 作为低精度训练项目 Owner，负责训练管线与数值稳定性验证；在训练框架中集成低精度训练方案，搭建算子、层与模型级指标监控及离线检查点分析工具，为混合精度配置与异常定位提供依据。

变化：直接点明责任范围，并解释监控与分析工具服务于什么工程判断。没有凭空增加提速比例或线上收益。

### 2. 从“支持 QAT”到机制与结果

原文：

> 在训练框架中支持量化感知训练，优化训练效率。

若材料明确包含优化器更新阶段的集成和基线对比：

> 在优化器更新阶段集成量化感知训练，将量化逻辑与参数更新流程结合；完成与 BF16 基线的实验对照，为评估量化训练方案提供依据。

若用户给出了实测结论，再把末句替换成准确的结果。“相同配置”“训练开销对照”“训练速度基本一致”分别需要实验设置、评估指标和实测结果支持，不由“完成 BF16 对照”或“优化训练效率”推导。

### 3. 从合作措辞到设计约束

原文：

> 深度对接芯片部门，参与软硬件协同设计。

若材料确实涉及量化方案与硬件约束：

> 围绕端侧模型的存储和推理算力约束，与芯片团队协同评估数值表示及量化方案，将硬件支持能力转化为模型训练与推理实现的设计条件。

变化：解释合作内容及其如何影响技术方案，不将参与协同包装为独立负责芯片架构。

### 4. 从科研宣传到可核验说明

原文：

> 提出新量化方法，显著提高模型性能，突破现有方案上限。

若原始研究资料支持连续松弛和敏感度调度：

> 针对离散量化中的梯度失配，构建连续松弛量化路径，并根据张量敏感度调整退火策略；在指定模型与训练预算下，与相同评测设置的基线比较量化后的性能恢复。

最终简历应填入已经核验的实际实验条件和结果；没有证据时删去“突破上限”等泛化结论。示例中的方法也不能移植到不涉及这些机制的项目。

## 补充论文证据时

只有需要丰富或核对研究内容时才检索，不为加图标等格式任务开展研究。优先使用用户提供的论文、官方论文页面和原文；对具体版本、表格、章节与实验条件做好工作记录。

核对以下容易改变结论的细节：

- 模型、参数规模、训练 token/步数预算、基线、任务集合与平均方式。
- 百分数与百分点。例如 50% 到 53% 是提升 3 个百分点，不能写为提升 3% 而不解释口径。
- 1.2 倍吞吐与提升 20% 的关系，训练吞吐与端到端训练用时、推理成本之间的区别。
- 离线校准成本与训练期间开销，权重位宽与激活位宽，存储节省与实际速度。
- 算法结构特性与整个系统的性质。例如局部量化点积免乘，不代表整个模型没有乘法。
- arXiv 预印本、会议录用、期刊发表、媒体报道是不同状态。

研究原文可以支持技术方法和实验结果，不能证明用户负责整项工作。新增事实核验不充分时，保留有依据的描述并说明缺口；不要用听起来合理的术语补齐。
