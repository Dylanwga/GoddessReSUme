# Word 精修与验证

## 以当前文件为底稿

先读取本轮输入，而不是直接运行旧的生成脚本。用户可能已经改了字号、位置、分组、文字、链接或页数，甚至在原输出文件上保存了新版。

将指定保留区域记录下来。对只加一个图标或恢复一行的任务，优先做局部修改；复杂文本框、分组和兼容分支经由高层库重新保存，可能出现与请求无关的变化，可使用范围清楚的 OOXML 补丁并保留其他 ZIP 部件。

局部任务保留未涉及的运行级格式。整体任务保留有意义的粗斜体强调以及字段、公式、超链接、编号、批注与修订状态，同时按目标版式写入字体、字号和颜色，不能因照搬原 `rPr` 而沿用旧字体。不要为方便处理而接受全部修订、删除批注或将公式转成图片。若修订视图影响了内容依据，先明确应核对的视图。

## 整体任务的默认版式

完整优化、新生成或统一格式时，按 [定稿版式规范](layout.md) 实现由一段经历图标派生的统一主题色及浅色条带，保留字体层级、日期对齐和图标体系。查看其两页脱敏图片，按需要读取脱敏样例 DOCX 的样式与对象；样例决定结构与深浅关系，实际颜色按当前选定图标替换，不能强制沿用样例颜色。局部任务继续以当前稿为版式依据。

## 逐段独立文本框

采用默认定稿版式的整体任务，必须逐段建立原生文本框，可分别选中、编辑和移动；用户明确要求流式正文时以其要求为准。局部修改不额外转换未涉及的区域。先列出内容单元，再建框，不按渲染后的每一行拆分。

| 内容单元 | 拆分要求 |
| --- | --- |
| 姓名、栏目标题、项目标题 | 每项单独一个文本框，标题与后续正文分开。 |
| 联系方式 | 每个设计行一个文本框；同一行的图标、链接及分隔符留在一起。 |
| 学校/公司抬头 | 每条一个可编辑抬头文本框，背景和图标可以与它组成一组；不同经历不得共用一个组。 |
| 背景、职责、技术实现、成果等正文 | 每个非空逻辑段落一个文本框；每条一级、二级项目符号也分别成框，标签与该段正文留在同一框。 |
| 论文题录 | 每篇论文一个文本框，作者、标题、会议信息及链接可以共同换行；不同论文分框。 |

例如“项目标题 + 背景 + 职责 + 两条技术分项 + 结果”应有 6 个独立文本框。一个条目自然折成两三行仍是一个框；同一框用多个 `w:p` 或 `w:br` 塞入多个条目仍未完成拆分。不能用整页/整段经历大框、表格、图片或整页分组替代逐段对象。仅限同一条带的背景、机构图标和抬头进行必要分组；项目各段不要锁在一个大组里。

1. 清点正文、表格单元格、已有文本框、公式、图片和页眉页脚。只读取高层库的 `Document.paragraphs` 会漏掉一部分对象。
2. 在字体正确的环境渲染源文件，记录页号与几何位置。PDF 可辅助获取位置；文本匹配分数高只能说明大部分对齐，不能证明没有漏掉某个短抬头。
3. 为新文本框设置可解释的名称、唯一对象 ID、锚点、页内坐标、宽高、内边距和换行方式。不同形状有不同坐标参照，分组内部还可能存在缩放与偏移；不能把所有坐标都当页面坐标。
4. 保留照片等独立对象以及与正文的关系。文本框能否完整容纳内容以实际渲染为准，`autoFit` 或固定高度本身不构成保证。
5. 核对内容逐项覆盖和每页视觉结果。跨页段落需专门处理，不能把横跨两页的文字塞入一个固定高度形状。

拆分前后保留段内 run、超链接、原生公式、粗斜体和完整字符。复制 OOXML 段落后，按 [字体写入与验证](layout.md#字体写入与验证) 处理整体任务的字体，避免源段落的直接格式覆盖定稿字体。创建文档后清点每个 `w:txbxContent` 的非空段落，连同普通正文与手动换行逐项检查；不能只确认文件“含有文本框”。

恢复缺失行时：从用户指定的权威文字来源确认内容，在最新版中定位邻近项目，复用对应的样式和结构。只有恢复确实需要腾出空间时才移动附近对象，不把整页恢复成旧版。

## 精确编辑 OOXML 时

- `mc:AlternateContent` 的现代 `Choice` 与旧式 VML `Fallback` 可能各保存一份相同文字。阅读和统计时选一个有效分支；修改同一可见文本框时，存在的兼容分支也应同步更新。
- 更新范围必须唯一定位。可组合原文字片段、对象名称/ID、相邻标题与页内位置；固定“第 8 个文本框”在后续用户编辑后不可靠。对象无法唯一定位时先检查，不盲目替换全部匹配项。
- 图片和超链接的 `rId` 只在所属 XML 部件的关系表中有意义。复制段落或图标时，保留或重建正确关系；尤其不能把 Scholar 的目标 URL 随图标复制给 GitHub。
- 新对象 ID 在有效分支内保持唯一。复制图形时检查 `docPr`、图片属性和编辑标记，避免无意复用身份。
- 修改现代图形和 VML 替代物后，检查相关的缓存表示。若所改形状的 `o:gfxdata` 等旧缓存确实过时，可按已验证路径移除或重建；不要清除整份文件的未知缓存。
- 不改的 XML 区域与 ZIP 部件尽量保持原样。验证关系目标存在、内容类型正确、ZIP 能读取；这些检查不能代替 Word 渲染。

## 图标与联系方式

优先使用用户提供的图标，其次是机构官方品牌资源。现有视觉体系适合时直接复用；本案例中的学校、企业和平台只是示例，不是每份简历必备的图标集合。

小图标一般嵌为文字前的行内对象，方便与文字一起移动。匹配邻近图标的视觉高度、基线与间距，保持原图比例；图片外沿透明空白会影响实际大小，应检查有效图形边界。需要裁掉空白时可用文档内裁剪，避免随意重绘商标。

从现有图标复制样式时，替换图片关系、名称和替代文本；不要带走原链接地址。给已有文字加图标时，保留原链接，除非用户同时要求修改。检查中发现疑似错误链接，可以简短指出，但不能猜测用户的主页或邮箱。

常用 OOXML 单位：1 pt = 12700 EMU，1 inch = 914400 EMU；字号和文字基线偏移常以半磅记录，段落间距常为 twip。按字段定义换算，不混用。

用户要求单行联系方式时：

- 使用要求的分隔符，如 `｜`，控制分隔符两侧间距。
- 保留可点击的电话、邮箱、Scholar 或 GitHub 目标；文字标签可以比完整 URL 短，但链接不能被省略成无效目标。
- 通过有效宽度、头像位置、字段标签和字体微调获得空间，避免先把文字缩到难以阅读。
- 无手动换行符不代表一行放得下；实际自动折行必须在渲染中检查。
- 以后用户改回多行或重新布置了头像，以最新选择为准，单行并非永久风格要求。

## 用清单检查遗漏

`scripts/docx_inventory.py` 是标准库只读脚本，可清点正常显示分支中的段落文字、公式文本、符号、链接与媒体。它按部件解析关系，并区分嵌套文本框与外层宿主段落，避免重复计数。比较时会报告空白归一化后的段落增减及字符计数差异。

拆框检查使用 `textboxes` 和 `structure_summary`：每个 `w:txbxContent` 有独立 `textbox_id`，对应段落的 `context.textbox_id` 和每框零基 `paragraph_indices` 可以定位多段共框；同组的两个框也分别计数。汇总区分文本框、普通正文及表格正文，并标记显式换行。逐项检查多段框、仍在普通正文/表格中的目标内容和用换行拼接的条目。编号符号由 `numbering.xml` 控制，不计为额外正文段落。

这些结构数据只是定位线索：一个框内的一段文字也可能通过手动换行拼接了多个内容单元；多个框也可能锁在同一大组中。样例有 39 个文本框，包括照片和机构图标的占位文字；这个数量不是新简历的目标。应核对实际内容与可独立移动的对象，不要求所有新文档都凑成相同框数。

用法：

```sh
python scripts/docx_inventory.py before.docx --compare after.docx > diff.json
```

解释报告时：

- **只改格式**：核对新增/删除是否仅为预期空格、换段或标签调整；文本整体相同也要核对关系目标和视觉位置。
- **拆段或重新排序**：段落计数变化可能是预期操作，字符计数辅助发现遗漏，但不能证明语义正确。
- **改写正文**：逐项对应原事实和新版表述，不要求机械字面相同；任何删除都应能由本轮需求解释。
- **PDF 为内容依据**：另行提取并目视核对 PDF。这个脚本只处理 DOCX，不能证明与 PDF 一致。

清单是候选问题列表，不是“通过/失败”判定器。它不会计算 Word 的页面流、编号显示文本或字段的动态结果；字体符号、复杂公式、分组形状及隐藏文字也需要视觉检查。脚本读取的是保留插入、排除删除的视图，不代表它接受或修改了文档修订。

## 渲染与差异判断

使用环境提供的文档渲染工具；先通过工作区依赖发现运行时与可用渲染器，不在 skill 中写死某台机器的用户路径或版本号。如果有 documents 技能，遵循其渲染和交付约定。

渲染后逐页检查：

- 中文、英文、数学符号和项目符号是否缺字或替换；先查字体可用性，不因渲染字体缺失而改坏正文。
- 文本框是否遮挡后一个标题、是否超出页尾，是否因行距或内边距裁切最后一行。
- 图标、文字与分隔符是否对齐，日期和右侧字段是否溢出，单行要求是否真正满足。
- 页数、论文顺序、段落层级和用户指定保留区域是否符合本轮需求。
- 整体任务是否使用选定图标派生的统一配色，并对齐定稿规范中的字号、条带、列对齐和文本框结构；偏离应能由内容长度、分页需要或用户要求解释。局部任务仅检查请求范围及必要的邻近调整。

局部编辑可在相同环境渲染前后文件，比较变更包围区域。差异只出现在请求范围内，是保留布局的有效证据；若其他区域也变化，检查文件、字体和渲染器，再判断是否需要修复。原有布局问题应与此次引入的问题区分，不能宣称已全篇修好，也不能未经请求大幅移动用户内容。

本次流程暴露的典型问题是：正文已复制但编号丢失、来源本身缺少公司抬头、同名文件被用户更新、内容丰富后固定文本框溢出、图标继承了错误链接。每次依据实际编辑检查相关问题，无需为每次小改都运行完整研究与重排流程。
